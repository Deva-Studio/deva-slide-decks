The basics

A CLI is a tool you use by typing

CLI stands for command-line interface. Instead of manually creating a project from scratch each time, you type one line into a terminal, and the tool does the work. Here, it sets up a whole project to scaffold a prototyping environment.

Why it's worth building one

1 command

Fast

Complex, repetitive, multi-step setup becomes one text command.

same in · same out

Repeatable

The same answers produce the same project every time, for every team.

Automatable

A head start for AI

The agent starts from a working base template instead of generating the project from scratch, so it spends tokens on the actual work.

npx …

Easy to share

One line anyone can copy into a README, a ticket or a chat, and an AI agent can run it too.

Requirements

What your CLI needs to work for everyone

git

A repo host

GitHub, GitLab, Azure DevOps or another, for the CLI's code, templates and releases.

npx

A way to distribute it

Publish to a package registry (npm, GitHub Packages, GitLab or Azure Artifacts) so anyone can run it. Keep it private for an internal system.

repo create

A repo for every project

The CLI creates one through the host's API or CLI (gh, glab, az repos) and pushes the first commit.

https://

Shareable prototype URLs

Each project deploys to hosting (GitHub Pages, GitLab Pages, Azure Static Web Apps, Netlify or Vercel) with a link to send.

tokens · SSO

Access

Credentials for the registry and repo host, so people can install the CLI and publish their projects.

The CLI ships like any package, and every prototype ends up with a repo and a URL

Staying current

Three things fall behind the design system

cli

The CLI

Its templates and packages are a snapshot. Release it with the design system, so npx create-ds-prototype@latest always starts from the newest version.

context

What Claude knows

Ship the context with the components

The design system team writes the guidance once, and publishes it inside the package: which components exist, when to use them, and what never to write.

The project's CLAUDE.md imports it instead of copying it. When the package updates, so does what Claude reads.

The guardrail reads its token and component map from the same package, so it can't fall behind either.

# product-page/CLAUDE.md · written by the CLI
Prototype for Brand A, built with @your-ds.

@node_modules/@your-ds/components/CLAUDE.md
@node_modules/@your-ds/tokens/tokens.md
@your-ds/components/      published by the DS team
├── dist/
├── CLAUDE.md             usage rules for Claude
├── components.json       every component and its props
└── guard-map.json        what the guardrail swaps in

Correct usage

Make the right component the easy path

Up-to-date context isn't enough on its own. Claude still has to pick the right component, use it as designed, and not invent a new one.

Tell

CLAUDE.md imports the catalog: every component, its props, and when to use it.

→
Look it up

Before writing UI, Claude asks the catalog: npm run ds:find "review".

→
Block

The guardrail stops raw values, plain elements, unknown props, and new components that copy one in the system.

→
Flag

If nothing fits, Claude composes from existing pieces and logs a request for the design system team.

Rules ask. Hooks enforce. And a missing component becomes a request, not a one-off.

What Claude writes

A guardrail blocks off-system and invented code

// .claude/settings.json
"PreToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{ "type": "command",
    "command": "node .claude/hooks/ds-guard.mjs" }]
}]
// .claude/hooks/ds-guard.mjs
const { tool_input } = JSON.parse(await readStdin());
const code = tool_input.new_string ?? tool_input.content ?? '';
const problems = [
  ...rawColours(code).map((c) =>
    `Raw colour ${c}. Use a token: ${tokenFor(c)}`),
  ...rawElements(code).map((el) =>
    `<${el}> found. Use <${componentFor(el)}>`),
  ...newComponents(tool_input.file_path, code).map((c) =>
    `New component ${c}. Use <${closestInCatalog(c)}>`),
];
if (problems.length) {
  console.error(problems.join('\n'));
  process.exit(2); // blocks the edit; stderr tells the agent the fix
}

Existing projects

A session-start check nudges toward updates

Prototypes outlive the version they were made with. When a session starts, the hook compares versions and gives the agent a short note.

// .claude/hooks/ds-check.mjs · registered under "SessionStart"
const installed = installedVersion('@your-ds/components');
const latest = await publishedVersion('@your-ds/components');
if (installed !== latest) {
  console.log(`Components ${installed} installed, ${latest} out`);
  console.log(`New: ${await newComponents(installed, latest)}`);
}
if (scaffoldVersion() < latestScaffold()) {
  console.log('Update with: npx create-ds-prototype update');
}
// SessionStart output is added to the agent's context

It nudges and never blocks. Updating stays the team's call.
